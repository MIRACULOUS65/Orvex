# 1. Purpose

This document defines the API surface of the SentinelPay Backend/Core.

The API is the communication boundary between:

```text
Customer / SDK
AI / Agent Services
Blockchain / Execution Services
Dashboard
Internal Workers
```

and the Sentinel Core.

The Core API must expose stable, typed, authenticated operations while keeping internal implementation details behind service boundaries.

The most important rule is:

> **The Backend API may request, evaluate, approve, and authorize. It must never provide an unrestricted bypass around deterministic policy and execution gates.**

# 4. API Design Principles

The API must be:

```text
typed
versioned
authenticated
tenant-scoped
idempotent where necessary
correlation-aware
fail-closed for financial operations
```

The API must never silently:

```text
upgrade authority
bypass policy
bypass approval
bypass simulation
execute arbitrary transaction data
```

---

# 5. API Versioning

Public APIs are versioned:

```text
/v1/...
```

Internal APIs are also versioned:

```text
/internal/v1/...
```

Breaking changes require a new major API version.

For example:

```text
/v1/decisions
/v2/decisions
```

Do not silently change the meaning of V1 fields.

# 6. Common HTTP Semantics

Use conventional HTTP methods:

```text
GET
POST
PATCH
DELETE
```

For stateful financial actions:

```text
POST
```

with idempotency support where applicable.

# 7. Common Request Headers

Recommended headers:

```text
Authorization
Content-Type: application/json
X-Correlation-ID
X-Request-ID
Idempotency-Key
```

Not every request requires every header.

Financial state-changing operations require `Idempotency-Key` where specified.

---

# 8. Correlation ID

Every request may supply:

```text
X-Correlation-ID
```

If absent, Core generates one.

The value must be propagated through:

```text
AI call
Execution call
Database/worker context
Audit
Telemetry
```

---

# 9. Request ID

Each API request has:

```text
request_id
```

generated by the server.

It identifies the individual API call.

`correlation_id` identifies the larger end-to-end workflow.

---

# 10. Idempotency-Key

Required for financial state-changing operations such as:

```text
POST /v1/executions
POST /v1/approvals
```

where repeated submission could have side effects.

The backend must return the existing logical operation when a duplicate key is detected.

---

# 14. Authentication Model

Public SDK/API callers may authenticate through the project's configured customer authentication mechanism.

Internal services use:

```text
service authentication
```

The API must distinguish:

```text
human operator
customer application
agent service
AI service
execution service
read-only auditor
```

Authentication proves identity.

Authorization proves permission.

---

# 15. Authorization Roles

Logical V1 roles:

```text
OWNER
ADMIN
OPERATOR
AUDITOR
AGENT_SERVICE
EXECUTION_SERVICE
READ_ONLY
```

Role is not the only authority check.

Agent capabilities and active policy remain separate controls.

---

# 16. Tenant Isolation

Every company-scoped request must resolve:

```text
company_id
```

from authenticated context.

Do not trust a caller-supplied `company_id` without validating that it matches the authenticated tenant.

All repository operations must be tenant-scoped.

Request:

```json

  "name": "Example Corp"
```

```json
{
  "data": {
```

# 21. GET `/v1/companies/:companyId`

Returns company metadata subject to authorization.

Never expose sensitive billing/secrets data through this endpoint unless explicitly modeled.

# 22. PATCH `/v1/companies/:companyId`


# 73. Execution API

# 103. API Idempotency Rules

Financial state-changing endpoints must use idempotency where a duplicate request could create duplicate effects.


Policy operations may also use idempotency or optimistic concurrency as appropriate.

# 104. Optimistic Concurrency

State-changing endpoints should support version checks where appropriate.

Example:

```json

  "expected_version": 7
}
```

```text
CONCURRENCY_CONFLICT
```

This prevents silent overwrites.
